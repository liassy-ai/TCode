# 设计 + 交接工作流（发起方）

把想清楚、写下来、交给下一个会话，落成三份产物：spec（决策）、plan（文件级执行）、HANDOFF（新会话入口）。目录不存在就先 mkdir -p。

## 第 0 步：调研并核实（最重要）

1. 读项目的索引文档（若有，AGENTS.md 通常指向它）和相关代码。
2. 核实，不要猜。任何关于 SDK、API、外部依赖行为的关键论断，都要去 node_modules 的源码或 .d.ts 或官方文档读清楚，并记下来源（file:line）。
3. 先盘现有 UI 和基础设施。常常已经有一半，设计只需补缺的那半。
4. 对比要落到结论。给对比表，说明为何排除其他方案。不要只罗列可能性。

## 第 1 步：写 spec —— .local/agent-work/spec/<topic>.md

决策层文档，回答「为什么这么定」，不含文件级任务拆解。内容：

- 背景和现状
- 目标和非目标
- 核心决策（对比表加机制一句话）
- 架构和代码落点
- 契约（参数 schema、跨进程类型、details 形状）
- 安全清单
- 里程碑
- 风险和已核实事实。列来源，未核实的标「待核实」。

## 第 2 步：写 plan —— .local/agent-work/plan/<topic>-plan.md

执行层文档，实现方照着做。内容：

- 阶段 0 冒烟验证：把 spec 里每条「待核实」变成可执行的断言脚本，给出通过标准。失败就发帖到频道，禁止绕过。
- 后续阶段按文件拆任务：每个任务写清改或建哪个文件、怎么做、加哪些测试。
- 验收清单：typecheck、lint、test 全绿，加逐条手动测试和收尾纪律。
- 明确不做的清单。
- 引用 spec，不要复述。

## 第 3 步：建频道 —— .local/agent-work/channel/<topic>/HANDOFF.md

新会话的唯一入口。要自包含，不依赖聊天历史。包含：

1. 一句话任务和完成定义。
2. 必读顺序：HANDOFF、spec、plan、AGENTS.md 及其索引。
3. 关键约束：项目通用纪律，加本任务的硬约束。
4. 已核实事实表（事实、来源）。实现方直接采信，不要重新核实。
5. 待决事项。
6. 沟通协议。
7. 自动唤醒说明：实现方开工时订阅本频道，你的 channel_post 才能唤醒它。
8. 发起方也要订阅：建好频道后立刻 channel_subscribe({ topic })，否则通知链是单向。

### 沟通协议（写进 HANDOFF）

- 实现方：进展、阻塞、决策写进 IMPL-NOTES.md；完成时写 DONE.md。
- 评审方：反馈写进 REVIEW.md；实现方复工前先读。
- 阶段闸门（双方交替，最重要）：一个阶段完成等于 git commit（本地，不 push）加写 IMPL-NOTES 加 channel_post（摘要含阶段 N 完成、commit 短哈希、下一步），然后停下（结束回合，不再有工具调用，等对方）。评审方被唤醒后跑回归，写 REVIEW.md，用一条帖回复（明确放行或不放行），再停下等实现方。双方严格交替，不并行。
  - 原因：agent 回合在跑时，对方的帖子投递不进来。实现方停下，工作树静止，评审结论才可信。不停就是边测边改，中间态让测试失去意义。
  - 代价是串行、吞吐低，换来零冲突和可信结论。
- 实现方的完整指令在 channel-pickup 技能里。HANDOFF 只写结论。
- spec 或 plan 与代码冲突：停下，在频道留消息，不要自行绕过。
- channel_post 才通知对方。写完一批文件发一条摘要帖。纯格式或无信息的改动不发帖。禁止碎帖和分次回复。
- 终态退订：任务结束，发起方发 channel_post({ closed: true })，订阅方收取后退订。

## 第 4 步：收尾

不要把 spec、plan 文件放进项目索引。索引最多标出 .local/agent-work/ 目录。HANDOFF.md 带完整路径。没索引就跳过，不要新建。

交付后（用户已开实现会话）：你要传达信息，就写文件加发一条摘要，不要等用户转达。零信息不发帖。

作为评审方的节奏：被「阶段 N 完成」唤醒，此时工作树静止，正是跑回归和读 diff 的窗口，写 REVIEW.md，用一条帖明确表态，停下等实现方。不要在实现干活期间零散喂反馈。

回复用户：产物清单、关键决策摘要、以及「新会话从频道里的 HANDOFF.md 进入」。

## 反模式

- 把实现细节堆进 spec，或在 plan 里复述设计论证。
- 把未核实的 API 论断当事实。
- HANDOFF 里写「见上面的讨论」。
- 高频碎帖或零信息帖。
- 做完一阶段就顺手开下一个。
- 协议里写「发帖等评审」却不定义「停」。
